# Decision log

Dated, append-only. Newest at the bottom. Each entry: what was decided and why, so future sessions do not relitigate.

## 2026-08-16/17: Computation

- **OSM as the single road source**, snapshot 2026-08-17. Distances are to mapped ways; unmapped private tracks exist in reality. Neighbouring countries' roads count, so border spots are scored honestly.
- **Two scenarios instead of one**: A (any drivable way, tracks included) answers "how far from anything drivable", B (tracks excluded) answers "how far from real roads". Both are legitimate and they crown different poles, which is the interesting finding.
- **25 m coarse pass + 5 m refinement** (EPSG:3346, EDT then exact vector distances; see README). The published web raster is a separate 50 m grid, small enough to ship (site/data ~5 MB).

## 2026-08-17: Site and hosting

- **Plain HTML/CSS/JS, no build step, vendored Leaflet 1.9.4.** Longevity and zero maintenance beat framework comfort for a site this size; any future session can edit it without a toolchain.
- **Cloudflare Workers (static assets) as primary, GitHub Pages as mirror.** Static serving on Workers is free and unlimited; Pages is the redundancy and the CI exercise. Both deploy from the same repo.
- **Public repo under the personal GitHub account** (donataskasp), with a repo-local git identity so work identity never leaks into commits.
- **workers.dev URL lock-in accepted for now.** A custom domain (~10 EUR/yr) is deliberately deferred until the Europe version makes the project permanent.

## 2026-08-17/18: UI (v2-v5)

- Satellite is the **default basemap** (bogs and forests read better); OSM a click away.
- Map controls live in a **floating top-right cluster** (basemap, bands toggle, legend, selected-spot readout); clicking the brand resets the map; language defaults to the browser (lt if the browser says lt, else en), hash and localStorage override.
- **Mobile (<=720px) collapses the readout into a bottom-anchored pill** above the attribution. Rule established: mobile-only changes must leave desktop byte-identical (verify with sha256 screenshots).

## 2026-08-18: Analytics

- **Three layers, each honest about what it sees**: raw asset requests (volume, sees everyone, coarse), CF Web Analytics beacon (referrers/countries but blocked by Brave/uBlock, treat as a sample), and the **edge logger as ground truth**: the worker writes one Analytics Engine data point per GET of `/`.
- **GDPR by design, not by banner**: no IPs, no raw user agents, no cookies, no unique identifiers. Consequence accepted: we count page loads, not unique visitors. Browser/OS stored as coarse families; referrer stored as www-stripped host only.
- **Beacon kept anyway**: costs nothing and is the only signal for the GitHub Pages mirror, which has no server side.
- **Workers Analytics Engine over a VPS or self-hosted analytics**: free tier (100k writes/day) is ~1000x headroom, no server to babysit, and blockers cannot see server-side logging at all.

## 2026-08-20: Europe planning session (spec and plan approved)

Full reasoning in `docs/EUROPE_SPEC.md` and `docs/EUROPE_PLAN.md`; the kickoff brief is `docs/EUROPE_KICKOFF.md`. Numbers were fetched, not guessed: Geofabrik europe 32.4 GB, north-america 18.0 GB; the Europe extract polygon ends at 46.75E; Workers static assets cap at 20,000 files and 25 MiB each; R2 free tier is 10 GB, 10 M reads a month, free egress; this machine is an M4 Pro, 24 GB, 233 GB free.

- **Hero is "poles plus a continental explore layer"**, not poles-only and not explore-first. The per-unit headline numbers are what people repeat; the explore layer ("how remote is my cabin") is the personal, shareable part and the reason to compute the whole continent rather than 45 country runs. Opens on the visitor's own unit from the request's country and region code (never stored), with an opt-in locate-me button. Offline use remains the app's job; nothing in v1 blocks it.
- **Unit = country, main territory only.** Svalbard, Jan Mayen, Franz Josef Land, Novaya Zemlya, Azores, Madeira are masked: a roadless archipelago would top Europe at 100+ km and teach nothing, the European version of the Alaska problem. Microstates stay in. Units are admin-level-configurable so North America ranks states and provinces.
- **Russia: roads count, not a unit.** Owner decision (the war); also the extract only holds a slice west of the Volga, so a real "Russia to the Urals" would need a separate extract and a manual cut, then win by an order of magnitude. The explore layer still covers the slice so the map has no hole, minus a 50 km data-edge band.
- **Turkey and Georgia in whole**, flagged transcontinental; contested borders as mapped in OSM, footnoted. Self-review found their borders with Syria, Iraq, Iran, Armenia, and Azerbaijan are data edges, so those five become road-only supplement extracts (about 1.5 GB), the same trick the LT run used with its neighbours.
- **Scenario A is the headline, B secondary.** A can only under-report; B over-reports wherever a drivable track exists, and "20 km from a road" contradicted by a track is the public failure mode. Physical drivability, not legal access. Water does not block. Explicit tag lists, tested.
- **v1 is a dated snapshot; automated refresh is a parked stage (#13).** Poles move over years, not weeks. When built: Hetzner box from a scheduled workflow, under 1 EUR a run, PR with a diff report, publish on merge only. An unreviewed auto-publish is how a wrong headline goes live, so it never exists.
- **Europe first, portable by construction; North America straight after** (owner: no waiting for a launch; runs are overnight on the Mac). A region is a config file; the coarse projection is a proj string, not an EPSG assumption (the kickoff's parked EPSG:3035-only design is replaced); units per region; no cross-region ranking ever.
- **Architecture: continental 250 m equal-area raster, tiled exact distance transform, branch-and-bound to exact UTM refinement, grayscale class tiles z0-z9 in PMTiles on R2, static Leaflet site on Workers assets.** Rejected: computing in web-mercator tile space (novel margin math where wrong numbers are invisible) and independent per-unit runs (11 billion cells, border seams). Rejected: vector isobands plus MapLibre (map rewrite for no user gain; MapLibre stays the fallback). Tiles carry the raw class value and the browser applies the palette, because a painted palette cannot be read back exactly from a canvas; dark-mode palettes come free.
- **Published data leaves git.** Archives on R2 under immutable snapshot keys, served through the bucket's own hostname (the worker's 100k free invocations a day would die on one busy evening of tile requests); small JSON plus `manifest.json` in git. Publishing is a manifest commit; rollback is a revert. The repo stays private.
- **Accuracy tiers**: poles exact; 50 m detail rasters around the top 10 per unit; 250 m explore layer (about ±0.2 km, shown as "about 1.2 km"). A 100 m continental layer is a one-line config change but roughly 4x the tile storage; deferred until real archive sizes are measured, not refused.
- **Class table**: 254 classes, 50 m steps under 2.5 km, coarser to "240 km or more" (the arithmetic did not reach 250), 254 edge-masked, 255 no-data.
- **Naming parked** (owner wants help later; English-first, short, language-neutral; "Atokiausia Lietuva" survives as the Lithuanian title of `/europe/lt`). **Domain at Hostinger**, nameservers to Cloudflare as the one-time human step. Old worker becomes a permanent redirect so the LinkedIn link never breaks; new Analytics Engine dataset, old one ages out.
- **Validation is a pipeline stage that blocks publishing**: independent geodesic re-check, land and unit membership, data-edge bound, half-cell grid-shift sensitivity, doughnut hole detection, reproduction of Lithuania's published 3.43 km and 6.67 km as the regression test, invariants, and a satellite contact sheet a human reviews in the PR.
- **Tests: pipeline math only**; screenshots for the site. The plan fixes stages, interfaces, named tests, and acceptance criteria and contains no implementation code (owner's rule for the planning session); each executing session writes its own step-level plan.
- **Tracking**: epic #6 with stage issues #7 to #13; `parked` label created for #13. Build on branch `europe`; `main` keeps serving the LT site until the cutover stage.

## 2026-08-20: Stage 1 implementation decisions

Made while turning `docs/EUROPE_PLAN.md` Stage 1 into the step-level plan (`docs/superpowers/plans/2026-08-20-stage-1-pipeline-foundation.md`) and during the first runs on real data. Each bullet is a deviation from or a refinement of the spec.

- **Tiled distance transform: exact below `max_distance_m`, saturated at it; the doubled-overlap loop is kept but bounded.** The spec's "recompute with doubled overlap until no cell is unresolved" does not survive the real frame: the Europe bbox (measured from `europe.poly`, lon -32.7 to 46.75, lat 29.6 to 81.5) contains Atlantic and Arctic tiles more than 1,000 km from any road, so unbounded doubling would need whole-grid windows of 10 GB or more per worker. A cell whose tiled result is at least the overlap has a true distance of at least the overlap, so clamping it to `overlap * res` is correct as "at least this far", and every value below the cap stays bit-identical to the untiled transform. Production sets the initial overlap to `max_distance_m / coarse_res_m` as the spec says, so doubling is only a safety net.
- **Europe `max_distance_m` raised from 150,000 to 250,000.** With saturation at the cap, the cap must be at or above the class table's top edge (240 km, class 253 "240 km or more") so that a saturated cell can never publish as a wrong "about X km". At 250 km the saturated value falls in class 253 by construction. Cost: the frame margin grows from 150 km to 250 km (634 M to 675 M cells at 250 m) and each tile window grows from 5296 to 6096 cells square. No unit pole in Europe comes within an order of magnitude of the cap; the poles stage must still fail loudly if a unit's best coarse value equals the cap.
- **Frame = bbox of the primary `sources` polygons plus `max_distance_m` margin, snapped outward**, reconciling the spec ("extract bbox plus a margin of max_distance_m") with the plan ("union of source polygons snapped outward"). The margin is what brings the supplement roads (Iran, Iraq, Syria, Armenia, Azerbaijan) into the raster without extending the frame to Iran's eastern border; the edge polygon for masking remains the union of sources plus supplements.
- **Snapshot date is the primary file's `Last-Modified` in GMT**, here 2026-08-19 for a file Geofabrik names `europe-260819.osm.pbf` in its md5 file. Geofabrik serves downloads through a 302 to a mirror (ftp5.gwdg.de on 2026-08-20), which honours `Range`; the md5 file names the dated file, so verification compares the hash only.
- **Container runtime on the Mac is colima plus the docker CLI (brew), not Docker Desktop.** Headless, scriptable, no GUI install for the owner, same Dockerfile everywhere.
- **Container base is `ghcr.io/osgeo/gdal:ubuntu-small-3.13.3`, which is Ubuntu 26.04 with Python 3.14 and osmium-tool 1.19; the Mac venv stays on Python 3.12.** GDAL (3.13.3) and osmium (1.19) are identical on both sides, which is what the pipeline's correctness depends on; the Python minor version differs. All pinned wheels install on both, and the suite is green on both. CI runs the tests inside the image, so the container (the future production environment on a rented box) is what CI proves; the laptop venv is the development convenience. Revisit only if a behaviour difference ever shows up.
- **Extract converts GeoJSONSeq in 256 MB chunks merged through a VRT union, and filters each source before merging.** GDAL's GeoJSONSeq driver makes a schema pass and rewinds, and `/vsistdin/` buffers only 1 MB, so the plan's pipe into ogr2ogr stops after about 2,000 features (measured). Worse, the reader holds about 6 bytes of RAM per byte of input: the 37.7 GB Europe highways export killed ogr2ogr twice (SIGKILL after 3 minutes; `ogrinfo` alone reached a 132 GB memory footprint), while a 1.5 GB prefix peaked at 9.3 GB whether or not a spatial index was requested. The file is therefore split at line boundaries into 256 MB chunks, each converted to an unindexed FlatGeobuf with up to 6 ogr2ogr processes in parallel, and the chunks are merged in one streaming pass through an OGR VRT union layer into the final indexed FlatGeobuf (FlatGeobuf to FlatGeobuf costs 0.5 GB per 4 M features). Text and chunks are deleted once the merged feature count matches. Every extract artefact now carries a `<file>.ok` marker so a rerun resumes at the first missing piece instead of repeating 35 minutes of osmium; the second failure had cost exactly that. Filtering each source PBF with one combined osmium expression before `osmium merge` avoids writing a 35 GB merged PBF; the combined filter over the 34.8 GB Europe file took about 3.5 minutes.
- **No spatial index on the road layers in stage 1, and no single FlatGeobuf above 50 M features.** The merged Europe highways layer (101,461,002 features, 24.5 GB, packed R-tree 4.33 GB) came out unreadable in GDAL 3.13.3: header fine, first feature fails with "Invalid size detected" in both read paths, spatial reads empty, while 4 M-feature files are fine. Rather than bet on the exact bug, the extract keeps any layer above 50 M features as unindexed 256 MB chunks behind an OGR VRT union (`<layer>.vrt` is the canonical handle for every layer; small layers still merge into one indexed file behind the same kind of VRT), classify writes `roads_A`/`roads_B` without an index, and gdal_rasterize reads unindexed input in a single pass (its AUTO mode picks the vector-iteration algorithm when the layer has no spatial index, with the raster held in cache). Stage 2 needs bbox queries and chooses its own structure with a measured limit; tracked in #16. Spec 3.2 said "FlatGeobuf with spatial index"; the format stays, the index moves to where it is needed.

## 2026-08-22: Stage 2 implementation decisions

Made while turning `docs/EUROPE_PLAN.md` Stage 2 into the step-level plan (`docs/superpowers/plans/2026-08-21-stage-2-poles-validation.md`) and during three Europe runs on the 2026-08-19 snapshot. Run 3 (2026-08-22, 0 blocking failures) is the run of record; its numbers are in spec 3.3. Each bullet is a deviation from or a refinement of the spec.

- **Country and unit polygons are assembled by `poles.boundaries` from the present members of each relation, not by osmium's area assembler.** Closed outer rings become polygons, inner rings become holes of the outer ring that contains them, an open outer line is closed along the data-edge polygon, and only the faces containing the relation's `admin_centre` or `label` node are kept; `closed_by_edge` is recorded per area so the cut is visible. Measured on the Europe extract: 69 admin_level 2 relations, 15,827 of 20,404 member ways present, 116 seed nodes, 59 areas in 37 s. The four countries stage 1 lost come back with the cut named in the log: ES 7 outer rings, FR 2 outer plus 1 inner, NL 9 outer plus 22 inner, NO 7 outer, all flagged `partial`. RU assembles from 4 outer rings and is the only area that needed edge closure; no unit is `closed_by_edge`. Ten relations outside the primary polygon (AF, IL, JO, KW, LB, MA, OM, PK, SA, TM) yield no polygon and are logged, not failed. Stays OSM-only and needs no per-country downloads. Closes #15.
- **Roads are served to stage 2 and later stages from `poles/roads/`: the highways layer split into indexed FlatGeobuf tiles of 5 degrees in lon and lat, queried by bbox with way-id deduplication and an optional `where`.** The FlatGeobuf spatial index limit in GDAL 3.13.3 was measured by bisection with a VRT union of `places.fgb`: 5.3 M, 10.7 M, 21.3 M and 42.6 M features (7.25 GB) build, read their first feature and answer a spatial query with the expected count; 63.9 M (8.14 GB, smaller per feature, so the writer is probably the broken side), 85 M and 105 M build without an error and then return nothing at all. The recorded safe ceiling is 40 M features per indexed file, and `TILE_DEG = 5.0` keeps Europe's densest tile more than 4x below it: 116 non-empty tiles hold 101,524,648 features (the 101,461,002 source features plus ways that cross a tile edge), the largest being `t_5_45` at 8.7 M features; the whole set is 28.9 GB and took 49 minutes to build. One structure serves refinement, attribution, check 1 and stage 3's detail rasters. No upstream GDAL issue was filed: the failure is reproducible only with a multi-hour synthetic build and the pipeline no longer needs the broken size. Closes #16.
- **A supplement country is never a unit, and that is decided by geometry rather than by a list**: a country is unit-eligible only if at least half of its area lies inside the union of the primary source polygons. Armenia, Azerbaijan, Iran, Iraq and Syria drop out on their own, Turkey and Georgia stay in and are flagged transcontinental, Akrotiri and Dhekelia assembles but carries no ISO code and is not a unit, and Russia is excluded by config while its roads still count. The result is 52 units, which is what `expected_units` now pins in `regions/europe.yaml` and in spec 2.1.
- **The branch-and-bound bound is `(coarse_m + 2 * half_diag) * (1 + pad)`, not the spec's `coarse_m + 2 * half_diag * (1 + pad)`.** The projection scale error applies to the whole coarse distance, so the spec's form under-bounds a 30 km pole by about 600 m at Europe's edge, which is enough to prune the cell that holds the true maximum. `pad` is the Tissot distortion at the cell from pyproj `get_factors` plus 0.002 for the UTM scale factor and the ellipsoid. The plan's "2 km dedup among candidates" is replaced by an exact dominance rule, and acceptance uses the **lower** bound of the ground distance (`hypot / (1 + pad_max) >= dedup_m`) with the dominance mask as its exact complement, so the exact geodesic recheck can never drop a pair the search accepted. No silent cap: a warning at 500 refinements per unit and scenario, a hard failure at 20,000. On the Europe run 12 of the 104 jobs warned; the worst was Luxembourg A at 3,588 refinements in 318 s, an order of magnitude below the cap.
- **Refinement inside a cell is one exhaustive 5 m sweep of the cell window in the local UTM zone**, not the spec's 25 m pass followed by a 5 m pass around the winner. The narrowed fine pass came 0.97 to 3.1 m short of the exhaustive sweep in review trials: the Lipschitz argument that justifies narrowing breaks once the allowed mask can reject the coarse winner. One sweep of a 250 m cell is 5,041 points (71 x 71 at 5 m, reaching 175 m each way) and a few milliseconds per refinement, cheap enough that the exact rule wins. The window is half the cell diagonal wide; the floor in `_axis` leaves 1.8 m of the 176.78 m half-diagonal unswept, which is inside the lattice's own 2.5 m half-step, so the cell is still covered to lattice resolution under any grid rotation.
- **Refinement points are restricted to the unit polygon, the land polygons, and outside water polygons of 1 km2 or more**, so a pole can never be published in the sea, in a lake, or across the border. Building the large-water layer exposed a GDAL 3.13.3 bug: the `ogr2ogr` Arrow fast path silently matches nothing when the filter is on the special field `OGR_GEOM_AREA`, so `water_big.fgb` came out empty with no error. Bisected across `-sql`, `-where`, with and without `-t_srs` and the index, and reproduced into GeoJSON; `--config OGR2OGR_USE_ARROW_API NO` gives the expected 25,028 features and a regression test now runs the real `ogr2ogr`.
- **Candidate cells are every cell the unit's allowed land touches, not the cells whose centre falls on it**: `units.tif` is `touched(unit) AND touched(land) AND NOT interior(big water)`, where interior water is a water cell centre whose cell does not touch the water boundary. This is a deviation from the plan's cell-centre rasterisation and from the cell-centre view of the grid that spec 6.4 assumes. Run 1 showed why: 24 of 104 grid-shift comparisons failed, and 8 of them were sub-cell islets that appear and disappear with the half-cell offset (Jabuka, Filfla, the Minquiers, Sandsundvaer, Slyne Head, an Aland skerry, Channel Islands rocks), plus one boundary sliver where Gibraltar's winner moved between 331 m and 548 m. A cell-centre mask makes the search depend on where the frame origin happens to fall; the touch rule does not. Because one all-touched raster hands a cell touched by several units to the highest index only, the stage writes two rasters (index ascending and descending) and reads their union; only a cell touched by three or more units can lose its middle unit, and none of the 918 published poles sits in one. The visible consequence is that offshore rocks now win poles, which is spec section 2.3's own rule (water does not block, roadless islands count) made visible; it is flagged to the owner on #8 as a publication choice, not a bug. The second consequence is that `area_km2`, which counts candidate cells, now overstates small units (Vatican 1.0 km2 against 0.49, Monaco 3.9 against 2.02, Gibraltar 10.4 against 6.8); stage 3 computes the published area geodesically from the unit geometry instead.
- **Check 1 densifies road geometry at 1 m before the geodesic measurement.** The recheck is meant to be independent of the search, so it measures to points on the way rather than to its vertices; 1 m is far below the 27.8 m largest absolute difference the check reports, and it costs 28 s on the largest unit (Greece A) and 375 s over all 918 poles, which is affordable at the once-per-run scale. A coarser step would make the check's own error comparable to what it is checking.
- **Check 4 passes when `|delta| <= max(1 %, 10 m)`, and a far move with an agreeing distance is a non-blocking tie.** Spec 6.4 line 204 says a winner that moves more than 500 m or changes by more than 1 % is an artifact and the unit fails. That rule fails on plateaus, where the number is right and only the coordinate is arbitrary: 15 of run 1's 24 failures were ties within a single cell or across one, including Vatican City gaining 1.4 m (1.09 % of a 126 m distance, so the percentage rule alone can never hold for a microstate) and Germany B moving 368 km for 9 m. The published number is the distance; the coordinate is one of possibly many equal maxima. The absolute floor of 10 m is what makes the check meaningful for small distances, and the shifted rerun searches the full `top_n` rather than the spec's top 3, so a unit whose rank 1 is excluded is still validated on the pole that will publish. Run 1's report is kept at `work/europe/2026-08-19/validate/report-run1.json` as the evidence. Run 3 with the touch rule and this tolerance: 104 of 104 pass, no ties needed.
- **A data-edge failure (check 3) excludes the failing poles, not the unit.** Spec 6.3 says a failing unit is flagged and not published, which would drop Georgia and Spain B entirely over poles ranked 5 to 10. Instead the failing poles go into an `excluded` list in `report.json`, the unit is flagged with the count, the contact sheet shows its first non-excluded pole, and the run continues; every other blocking check still stops the run. Run 3 excluded 9 poles: 7 in Georgia along the Russian border, Spain B rank 1 on Alboran (a true positive, Morocco is about 50 km south and outside the extract), and Iceland B rank 9 in Hornstrandir, where the flag is against a sea leg of the edge (#19). Check 4 follows: it compares the first pole that was not excluded, and when every pole of a unit and scenario is excluded the comparison is recorded with `all_poles_excluded` and does not block, because the shifted rerun searches the same incomplete road data and there is no pole left to publish.
- **Membership (check 2) is tested with a tolerance of 1e-6 degrees, which is exactly the rounding quantum of the published coordinates.** A strict point-in-polygon test on a coordinate rounded to six decimals misfires by design; it flagged two coastal poles (ee A rank 10, no A rank 1) that were 1 to 4 cm outside their own unit. The water test stays strict.
- **Check 5's thresholds are module constants** (`INNER_KM = 10`, `OUTER_KM = 30`, inner density zero against an outer density above the unit median), promoted to region config only when a region needs different values. Run 3 raised 6 hole warnings, all on Guernsey and Jersey skerries, none blocking.
- **Only Lithuania's poles block in check 6.** The two LT entries are the regression test and reproduce the published demo within 0.02 %; four external national poles (Sweden, Norway, Finland, Great Britain) were verified against their sources and are informative only, and three others plus a fabricated figure were dropped rather than guessed. The Finnish and British entries fail permanently by design because their road sets differ from both of our scenarios, and the report prints that difference next to the number.
- **Reference poles live in `regions/europe-refs.yaml`, named by the optional `references:` key of the region config.** They were loaded from a fixed path inside the package, and their top-level keys name one region's units (`lt`), so a North America run would have looked for Lithuania's poles and failed check 6 as blocking. Region configs are the only place a region is described; a region that names no reference file gets one passing, non-blocking check 6 saying so, so the report still lists the check. Found by the stage-2 final review.
- **Publish consumes the `excluded` list of `validate/report.json`**: it drops those poles, recomputes ranks within the unit, and refuses to run without `validate/done.json`; `A.json` and `B.json` stay as the search wrote them, so the search output and the published set are separately auditable. Two of run 3's nine excluded poles are unit winners (Georgia A rank 1, Spain B rank 1), so a naive publish would headline poles that validation refused. Issue #21. Found by the stage-2 final review.
- **Check 7's class-table and R2 HEAD parts run in stage 3**, where the class table and the upload exist. Stage 2's check 7 covers A <= B, `top_n` poles or a recorded reason, the 10 km separation, the unit count, and the structure of `poles/*.json`.
- **Fewer than `top_n` poles is a recorded reason, not a failure, when the unit is exhausted**: the 10 km discs of its accepted poles cover every candidate cell. Ten of the 52 units are short in run 3 (Vatican City, Monaco, San Marino and Gibraltar 1 each; Liechtenstein 3; Andorra 5 in A and 6 in B; Guernsey and Jersey 6; Malta 7; Isle of Man 7 in A and 8 in B), each with the reason in its JSON entry.
- **The territory mask grew twice during the runs, both times under spec 2.2's own rationale.** Svalbard's south edge moved from 76.0 to 74.0 N because Bjornoya (74.4 N) is Svalbard and its 2,842 roadless cells saturated Norway's search at the 250 km cap; Rockall joined the list for the same reason once the touch rule made a 20 m rock 300 km offshore a candidate cell. Both are config, not code.
- **A coarse value at `max_distance_m` stays a hard abort**, and the message now names the unit, the scenario, the cell count and the lon/lat of the saturated cell. A saturated cell means the region is misconfigured, not that the pole is far; silently searching it would publish the cap as a distance.
- **The poles stage caches each unit and scenario result under `poles/results/`**, cleared when `units.tif` is rebuilt, so a failure at job N keeps jobs 1 to N-1: the Bjornoya abort at job 59 of 104 had cost the whole run. The cache is not invalidated by a grid rerun, which is tracked in #18 along with the touched-land and water-interior intermediates that carry no frame stamp.
- **The contact sheet is delivered as a local file and an R2 object, not as an attachment.** `contact-sheet.html` is 10.9 MB with inlined satellite thumbnails; its path and a summary go on the stage issue for the owner, and stage 3 uploads it under `validation/` with the snapshot.

## 2026-08-22: Stage 3 implementation decisions

Made while turning `docs/EUROPE_PLAN.md` Stage 3 into the step-level plan (`docs/superpowers/plans/2026-08-22-stage-3-publish.md`) and during the Europe run of the stage's local part. That run (2026-08-22, commit 3b0dbd4, 962 s on the 2026-08-19 snapshot) is the run of record; its numbers are in spec 3.3 (the `publish (local part)` row and the paragraph after the stage-2 one) and spec 4.1 (archive sizes, bytes per km2, the 268.6 MB upload set). The upload and the HEAD verification are not in it: R2 is not enabled on the Cloudflare account yet, so they run later as a rerun of the same command. Each bullet is a deviation from or a refinement of the spec.

- **The explore pyramid comes from GDAL's own `gdal raster tile`, not from the custom Python tiler the plan sketched.** `gdalwarp` warps the class raster to EPSG:3857 at the z9 resolution (305.748 m per pixel) with `-tap` and nearest resampling, which lands the raster exactly on the tile grid because half the world extent is exactly 65,536 z9 pixels; `gdal raster tile` cuts the tiles, a Python packer writes them into MBTiles (TMS rows, blank tiles dropped) and `pmtiles convert` produces the archive. A maintained tool that already knows the scheme is one fewer place for an off-by-one in a tile index to hide. Where the overviews are built changed during the build, see below.
- **The edge mask is drawn from the union of every source `.poly`, the same polygon validation check 3 uses.** Its boundary buffered by `edge_mask_m` (50 km) in the coarse CRS is rasterized all-touched on the grid frame: land cells in that band become EDGE, cells outside the union and water cells become NODATA, everything else carries the class of its distance and saturated cells land in class 253 by construction. The frame's 250 km margin reaches into North Africa, the Middle East and Russia beyond the extract, and those cells have no honest distance, so NODATA is the only truthful value for them. Measured on Europe: of 675.4 M cells, 525.6 M are NODATA, 3.8 M are the edge band and 146.0 M carry a class, identically for A and B. The known cost is #19's: the band follows the `.poly` boundary rather than the true data edge, so an open-sea leg of that boundary masks cells that are in fact fully surveyed.
- **Publish drops every pole validation excluded, renumbers the rest, and refuses to run without `validate/done.json` (#21).** Each `(scenario, unit, rank)` triple in the `excluded` list of `report.json` is removed, the remaining poles of that unit and scenario are renumbered from 1, and the number dropped is recorded as `withheld` in both the units document and the unit document, so the withholding is visible rather than silent. An exclusion that matches no pole is a hard error ("rerun validate"), because a stale report against a fresh search cannot be reconciled by guessing. Two of run 3's nine exclusions are unit winners (Georgia A rank 1, Spain B rank 1), so publishing the search output as it stands would headline poles that validation refused. Detail rasters are keyed by the published rank, not the searched one.
- **Detail rasters are measured, not resampled from the 250 m grid.** The pixel centres of spec 3.5's EPSG:4326 lattice (`dlat` = 50 m in degrees of latitude, `dlon` = `dlat / cos(lat)`) are projected into the pole's UTM zone and measured against that scenario's roads with an STRtree nearest query, then classed with the region's own table so the overlay and the explore layer speak the same values. Pixels off land are NODATA and pixels inside the edge band are EDGE, under the poles stage's land rule minus the unit restriction, so a neighbour's land shows its real distances instead of a hole at the border. Roads are queried for the window grown by `dist_m` plus the window's half diagonal plus a kilometre of slack, which covers every road that can be nearest to any pixel. The PNGs are written with rasterio's PNG driver, so no image library joins the dependency list.
- **R2 is configured entirely by environment, and every secret is named by a path rather than carried as a value.** `POLES_R2_ACCOUNT_ID`, `POLES_R2_BUCKET`, `POLES_R2_TOKEN_FILE` (the Cloudflare API token with R2 admin read and write, used through the REST API for bucket creation, the managed `r2.dev` domain and CORS), `POLES_R2_ACCESS_KEY_ID_FILE` and `POLES_R2_SECRET_FILE` (the S3 pair that does the uploads), plus an optional `POLES_R2_BASE` for the public base URL. A token in an environment variable ends up in a shell history, a process listing and a CI log; a path does not, and nothing under the repo holds either. Missing variables or unreadable files raise `PublishError` naming them and pointing at `pipeline/README.md`.
- **CORS on the bucket allows any origin**, methods GET and HEAD, any request header, with `Content-Length, Content-Range, ETag, Accept-Ranges` exposed and a max age of 86400. The bucket is public read-only data, and the site reaches it from at least three origins before the cutover (a local server, the preview worker, the custom domain); an origin list would have to be edited again at each of those and protects nothing that is not already public.
- **The upload set is the two archives, everything under `detail/`, and stage 2's three validation artefacts,** keyed under `<region>/<snapshot>/`, immutable (`Cache-Control: public, max-age=31536000, immutable`), content type by extension, 8 uploads in parallel, and an object whose size already matches is skipped. Verification is spec check 7: a HEAD on every key must answer 200 with a size, and a 16 KiB range GET on each archive must answer 206, because an archive that downloads but does not serve ranges is useless to the site. The site documents are deliberately not in the upload set: they are committed to git, and publishing is the manifest commit. `regions.json` carries the base URL as `r2_base`, the managed `r2.dev` domain until stage 6 puts a custom domain in front.
- **The site documents are written last, after verification, and merged per region.** They go to `publish/site/` and into the site directory (`--site-dir`, default the repository's `site/data`; `--no-write-site` keeps them in the work directory only). `regions.json` and `manifest.json` are merged by region id with whatever the target already holds, so publishing North America later cannot drop Europe. Every document is validated against the JSON schemas in `pipeline/poles/schemas/` before it is written; those schemas are spec 4.2's contract frozen in files, with `additionalProperties: false` at the top level, so a field the site does not know about cannot appear by accident.
- **Unit area (#20) was fixed by the plan as the geodesic area of the unit outline in `units.fgb`,** on the grounds that stage 2's candidate-cell count overstates microstates. The build reversed it, see the area bullet below: the OSM outlines include territorial waters, which is a much larger error than the one being corrected.
- **Regional rank is computed per scenario, not once on the A distance.** Units are ordered by their published rank-1 distance descending, dense ranks from 1, ties broken by unit code, and a unit with no published pole in a scenario carries `null` for that scenario. B crowns different units from A, which is the reason there are two scenarios at all; a B leaderboard sorted by A distances would be wrong on its face.
- **The class table has one definition in Python and one mirror in `site/js/classes.js`, with a test that compares them.** The mirror is an ES module with no DOM dependency so node can import it; the pytest suite runs node on it and compares every edge when node is on PATH, and skips with a message when it is not. `site/js/classes.test.html` is the hand-opened browser check. A table that drifted between the two sides would mislabel every distance on the site with no error raised anywhere.
- **The stage was built and run in two halves on purpose.** Everything that does not need R2 was implemented, tested and run on the real snapshot now; the upload and the verification wait for the owner to enable R2 on the Cloudflare account and then run as a rerun of the same command with the environment set. #9 stays open with exactly those boxes. Blocking the whole stage on an account setting would have idled the build for no gain.
- **Outlines are densified before every reprojection, the way the grid stage already does it.** Transforming only the vertices of the source-polygon union put the 45 E meridian leg of the real union 41 to 69 km off its true position, which would have masked or exposed the wrong cells along the entire eastern edge. Found by the task-2 review; the cost is a few seconds.
- **A stale `.ok` marker is unlinked before its artefact is rewritten**, the extract stage's convention. Otherwise a crash in the middle of a rewrite leaves a marker beside a half-written file and the next run trusts it.
- **The tile overviews are built by the packer, not by GDAL, which amends the tiler decision above.** `gdal raster tile` cuts z9 only (`--min-zoom 9 --max-zoom 9`, alpha kept, `--webviewer none`); the packer folds alpha 0 into NODATA, re-encodes single-band grey PNGs, and builds z8 down to z0 itself as the mode of each 2 by 2 block, with a data class beating NODATA and the lowest data class winning between data classes. GDAL's own mode overviews count the zero fill under transparent pixels, and zero is a real class (the nearest-road class), so they invented a class 0 fringe along every coastline below z9: 87 of 25,725 opaque z8 pixels on a synthetic coast. `--no-alpha` was dropped for the same reason, since GDAL fills uncovered area with 0. The cost is speed: the Python packer takes about three minutes per scenario against eight seconds for the GDAL cut, and it is the slow step of the stage.
- **Detail jobs are per unit and scenario rather than per pole, with one road cache each,** so the poles of a unit share the road reads that dominate their cost. An empty road set inside a padded window is a hard error, not a remote window: the pole's own nearest way lies inside the window by construction, so an empty set means the road tiles and the published poles disagree. Each job carries the region's class edges, so a worker renders with the same table as the explore layer.
- **The all-NODATA guard on a detail raster is a distance rule, not a pixel count (#27).** If the nearest land in the window lies more than 100 m from the pole, or there is no land at all, the run fails; within 100 m the blank raster is published with a warning. A zero-pixel rule aborted a real run twice on legitimate skerry poles: Bell Rock is a 14 m square and no 50 m pixel centre can land on it. Five of Europe's 909 rasters are blank under this rule (Bell Rock for gb A rank 6 and B rank 7, Kolbeinsey for is A and B rank 1, a Pembrokeshire rock for gb B rank 4), so the site has to render a pole with no overlay. #27 records the other end of the same geometry: the road query pad stops being safe above about 80 N with far poles, and Europe tops out near 71 N.
- **The published `area_km2` is stage 2's land-cell area, not the geodesic area of the unit outline, which settles #20 differently from its title.** The outlines in `units.fgb` come from OSM boundary relations and include territorial waters: Malta measures 4,354 km2 that way against 347 km2 of land cells. The plan's `unit_area_km2` helper and the geometry plumbing behind it were dropped rather than kept for a caller that no longer exists. What stays wrong is the cell count's own overstatement of the smallest units (Vatican City 1.0 km2 against 0.49), a few percent of one displayed number on a handful of units.
- **`nearest_place.name` is nullable in the pole schema.** Five of Europe's 918 poles attribute to an unnamed hamlet, and both alternatives lose information the site can state honestly: inventing a name, or dropping an attribution that is otherwise correct. A unit's `name` and `name_en` stay required. Stage 4 has to render the null case.
- **A detail raster's completion marker is its JSON sidecar, not an `.ok` file.** The sidecar is written after the PNG and it is what the site needs in order to place the image, so it cannot drift from its raster the way a separate marker can. The cost is that `publish/` carries two resume conventions: `.ok` markers for the class rasters and the archives, sidecars for the detail rasters.
- **`detail/published.json` fingerprints the published pole set (scenario, code, rank, lat, lon, sorted), and a mismatch or `--force` clears and rebuilds `detail/`.** The rasters are keyed by published rank, so a validate rerun that changes the excluded list followed by an ordinary publish would have served the wrong picture for a pole with no error anywhere. The stamp is written after the clear and before the render, so a crash mid-render still triggers a rebuild. Found by the task-7 review.
- **`pipeline_commit` in the manifest is null on a dirty tree, with a warning in the log.** A hash that does not describe the code that ran is worse than no hash at all, because the manifest is what makes "data and the code that produced it are committed together" auditable. It is null in the container too, which the schema allows.
- **The R2 client makes one attempt plus three retries at 1, 2 and 4 seconds on 429 and 5xx, and treats verification problems as findings rather than exceptions.** An unreachable host, a HEAD without a `Content-Length` and a failed range probe are all listed failures, so one run reports everything wrong with the bucket instead of stopping at the first. Uploads run two parts in flight per file, since boto3's default of ten is aimed at a machine that is not also holding a continental grid. API error bodies are quoted to 200 characters, and no message can contain a token.
- **`done.json` carries `disk_bytes` for every stage, written by the runner, and the publish-specific size field was dropped.** One measurement in one place beats a per-stage field that each stage computes its own way.
- **The local part of the stage completes before the R2 configuration is read.** Masks, archives and detail rasters are built first, so a machine without the credentials still does the whole compute; only then do missing variables stop the run with a `PublishError` naming them. No `done.json` is written, and a rerun with the environment set resumes at the upload from the markers.
- **The explore chain is fingerprinted by `publish/inputs.json`, and a change or `--force` resets the whole chain (final-review fix round).** The stamp holds the class edges, `edge_mask_m`, and the size and mtime of every grid raster and `.poly` file the chain reads; on a mismatch or a forced run `_reset_explore` removes every `publish/*.ok` marker and the `publish/tiles_*` directories before anything is built, so no marker can resume over an artefact made from older inputs. A missing stamp beside existing artefacts adopts them and writes the stamp, which keeps the Europe run of record on disk valid under the new code. The detail stamp gained the class edges and the sha256 of the edge band for the same reason (the rasters class with the edges and burn EDGE inside the band), which costs one rebuild of `detail/` (about 8 minutes) at the R2 rerun.
- **Text files a resume or the site depends on are written atomically** (`write_text_atomic`: tmp file beside the target, then `os.replace`): the detail sidecars, both stamps and the site JSON. A kill mid-write leaves the old file or none, never a truncated one.
- **The Mercator extent of the class rasters carries one z9 pixel of margin per side** before `-tap` snaps it: the extent is estimated from 200 samples per frame edge, and a denser sample can exceed the estimate by a fraction of a pixel.
- **A forced run re-uploads every key**; an unforced run skips keys whose size on R2 already matches.

## 2026-08-23: Stage 4 implementation decisions

Made while turning `docs/EUROPE_PLAN.md` Stage 4 into the step-level plan (`docs/superpowers/plans/2026-08-22-stage-4-site.md`) and while building the site on branch `europe` on 2026-08-22 and 2026-08-23. The site was written and verified against the local run of record through a development harness, because R2 is still not enabled on the account and `site/data/` therefore holds no region JSON. Each bullet is a deviation from or a refinement of the plan.

- **A development harness under `dev/` makes the site testable end to end before R2 exists.** `dev/serve.mjs` puts three roots on one origin so the browser needs no CORS: `site/` with the SPA rule the Workers assets binding applies in production, the dev JSON under `/data/` (falling back to `site/data/`), and `work/<region>/<snapshot>/publish/` under `/r2/<region>/<snapshot>/` served with HTTP range requests, which is exactly what the pmtiles library needs and what R2 will do. `dev/site-json.py` builds the four site documents from the run of record and rewrites their `r2_base` to that local server; the schemas require an `https://` base, and rightly so, so the documents are validated with a placeholder and the local base is substituted afterwards. A miss under `/data/` or `/r2/` is a 404 and never the SPA page, so a wrong prefix fails loudly instead of feeding `index.html` to a parser that expects JSON or tile bytes. The alternative was to wait for R2 and build the site blind; the harness cost one file and turned the whole stage into ordinary work against real data.
- **The preview is a second wrangler environment of the same worker on the same account, deployed from `europe`.** `wrangler.jsonc` has an `env.preview` block with its own name (`atokiausia-lietuva-preview`) and its own analytics dataset; `deploy-cloudflare.yml` passes `--env preview` on any branch that is not `main` and points its checks at the preview URL. One worker source, one account, no second repository and no second set of secrets, and the branch test is written as "not main" so that an empty expression value can only ever route a deploy to the preview, never to production.
- **The Analytics Engine row grows to eight blobs and goes to new datasets, `poles_views` and `poles_preview_views`.** The first six blobs keep the LT site's order and meaning (country, colo, referrer host, browser family, OS family, hostname) and the two new ones are the landing region and the landing unit from the path, which is what makes a per-region and per-unit read possible at all. A new dataset rather than the existing one, because `atokiausia_views` holds six-blob rows and the stats queries in `CLAUDE.local.md` keep reading it until the cutover; appending a differently shaped row to the same dataset would have made every historical query ambiguous. The preview gets its own dataset so test traffic never lands in the real numbers.
- **The visitor's location comes from `request.cf`, stamped into the page as a meta tag, not from the browser's geolocation API.** The worker writes `<meta name="visitor" content="LT">` (or `US-AK`) into `head` with HTMLRewriter, and the site reads it to choose the opening unit. The data Cloudflare already attaches to the request is coarse and free; a geolocation prompt on the first screen is a permission dialog before the visitor has seen anything, and most people say no. The meta value never leaves the visitor's own page. The value's shape is enforced in the worker, since it is written into HTML, and re-checked by the site before use. `navigator.geolocation` is still what the "Locate me" button uses, because that is an explicit request by a visitor who wants their own position on the map.
- **"Locate me" resolves the visitor's unit by bounding box: units whose bbox contains the point, preferring one whose country matches the visitor meta, then the smallest unit by published area.** The site has no unit outlines and the first screen has a byte budget, so the honest choices were a bbox test or shipping polygons for every unit up front. Bounding boxes overlap (a coastal point can sit in two countries' boxes, and a small unit's box can sit inside a large one's), which is why the country from the visitor meta breaks the tie first and the smaller unit second. The proper fix, lazy unit outlines fetched on demand and a point-in-polygon test, is #33.
- **The screenshots live in `docs/screenshots/`, not under `site/`.** Everything under `site/` is deployed by the assets binding, so review images kept there would be published, counted in nothing, and served to visitors who never asked for them. `docs/` is the right home for a review artefact, and `docs/screenshots/README.md` states the set and the rule that goes with it.
- **The screenshot routine stubs the basemap tiles with a flat grey tile and starts its own server.** An image that changes when Esri reshoots an area or OSM restyles a road is not a test, and one that fails when a tile host is unreachable is worse. What stays real is everything the project produces: the explore classes, the detail overlay, the markers and the whole interface. The six desktop images are byte-identical run to run, which is what the phone-only rule needs; the phone images can differ by a few pixels of antialiasing around a marker, so they are compared by eye.
- **Playwright is installed outside the repository, and the routine loads it through a CommonJS `require`.** The no-build-step property means no `package.json` and no dependency tree in the repo, so the browser lives in a scratch directory named by `NODE_PATH`, or in a gitignored `dev/node_modules`. ESM `import` ignores `NODE_PATH`, so a plain `import ... from 'playwright'` would only ever find an install inside the repository; `createRequire(import.meta.url)` honours both locations.
- **The hand-opened browser page `site/js/classes.test.html` is deleted and its assertions run in `dev/tests/classes.test.mjs`, which reverses the stage-3 decision recorded above.** Everything under `site/` is deployed by the assets binding, so the page shipped to visitors as part of the site; nothing test-shaped stays there. The node suite now runs the same cases (the edge count and the sentinels, the distance-to-class table, a doubled per-region table, and the four rejections) on every run instead of waiting for someone to open a page by hand. The Python-to-JavaScript mirror check in `pipeline/tests/test_classes.py` is unchanged and is still what catches drift between the two tables.

## 2026-08-23: Stage 5 implementation decisions

- **North America `max_distance_m` raised from 400,000 to 500,000.** The region's first poles run aborted on Nunavut: 36,600 of its 32.7 M candidate cells sat at the 400 km cap, and the stage refuses to rank a saturated cell (a cell at the cap means "at least this far", not a measured distance). An uncapped distance transform over the Canadian Arctic, run from the same road masks, puts the true maximum at 429.2 km in scenario A and 439.3 km in scenario B, both on northern Victoria Island near lon -108.0, lat 73.1; the Northwest Territories top out at 371 km and no other unit passes 300 km. 500 km clears the measured maximum by 60 km, more than any plausible road edit between snapshots moves a distance, and stays far above the class table's top edge (240 km). Alternatives: a `territory_mask` entry over the cell (wrong, this is a real pole on a large island, not an islet); 450 km (10 km of headroom over scenario B, one retagged winter road away from the next abort); 600 km (safer still, but each EDT window grows to 8896 cells square, about 6.6 GB per worker, for headroom nothing in the data asks for). Cost: the frame margin grows by 100 km a side (1.84 B to 1.91 B cells at 250 m), each EDT window grows from 7296 to 8096 cells square (about 4.5 GB to 5.5 GB per worker by the stage's own estimate), and the grid, the unit rasters and the search are rerun once. If the cap is still too low one day, the poles stage aborts loudly as it did here, and the cost is one more grid rerun.
